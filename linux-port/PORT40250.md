# [40250] Linux port — what the port does, and why

The companion to
[`patches/0001-r40250-linux-port.patch`](patches/0001-r40250-linux-port.patch).
The patch is the port; this explains it.

The target is the **[40250] Reference Serverfile**: source, server data,
database and client all from 40250. An earlier attempt targeted a *different*
Metin2 fork by mistake; see [RUNTIME.md](RUNTIME.md) for how that was caught and
why the two are not interchangeable. The method and the engineering findings of
that attempt carried over into this document; its file names, line numbers and
dependency versions did not, which is why its working notes are not kept here —
every version number in them belongs to the other fork.

Finished. The server builds, boots, serves real clients, and runs in Docker.

The whole of it is **30 files, 68 hunks, +1999 / −40 lines**. A fresh extraction
of the upstream archive plus the patch reproduces the tree the running server
was built from byte for byte — matching manifest hash, `patch` exit 0, zero
fuzz, zero rejects.

**One of those thirty files is not the port.** The port changes no behaviour: it
is the same server, running the same way, on a different operating system. The
`mysql_direct_query` binding in `game/src/questlua_global.cpp`, and the few lines
in `game/src/questmanager.cpp` that start the web panel's helper quest at boot,
are a feature the r40250 server never had. They are in the same patch because
they are a change to the same source tree, and they are labelled so that being
in the same file does not blur the line: every added line carries the marker
`M2_FEATURE quest-sql-binding`, and the patch's own header has a section named
*WHAT IS NOT PART OF THE PORT* listing them, emitted by `make-patch.sh` from
those markers rather than written by hand. `grep -n M2_FEATURE` on the patch is
the entire audit — if it returns anything not named in that header, something
has been added without saying so. The feature itself is documented in
[`../files/ADD_SQL_BINDING.md`](../files/ADD_SQL_BINDING.md).

## What the audits found

Better than feared. The tree has already been through a modernisation pass:
**zero** occurrences of `std::auto_ptr`, `bind1st`, `mem_fun`, `unary_function`,
`random_shuffle`, `register` as a storage class, or dynamic exception
specifications. Endianness is a non-issue — both platforms are little-endian, the
only 8 byte-order calls are correct IPv4 handling, and there is no manual
swapping anywhere. `strlcpy`/`strlcat` need no implementation: glibc 2.38
(Ubuntu 24.04, Debian 13) provides both. libthecore's `stdafx.h` declares them
only when `__GLIBC_PREREQ(2,38)` says the libc does *not* have them, so the
declarations never clash with glibc's own `__restrict`-qualified ones; since
every module includes that header, every call site is covered from one place.
**On a glibc older than 2.38 the port does not link** — an implementation would
have to be added. The images are Ubuntu 24.04, so this has never come up.

Also confirmed absent: `arc4random`, `qsort_r`, `sysctl`, `setproctitle`,
`getprogname`, `pidfile_*`, `closefrom`, `funopen`, `strtonum`.

`-m32` does a lot of work for free: `long`, `void*`, `size_t` and `clock_t` are
all width-identical to FreeBSD/i386, so ~110 `long` fields in packed wire structs
and every pointer field are safe without touching them.

## The two blockers that were not what they looked like

**The reported `boost/__typeof/__typeof.hpp` "hard error" was a false alarm.**
It is byte-identical in the pristine reference — not damage from a `sed` pass —
and it sits inside `#ifdef __WIN32__`, so it never reaches a Linux or FreeBSD
compiler. On Linux `__typeof` is the GNU builtin keyword; that is precisely why
the source uses it and only emulates it via Boost on MSVC.

**The real blocker was hiding behind it.** `libthecore/include/stdafx.h`
contained:

```c
#ifndef false
#define false 0
#define true (!false)
#endif
```

In C++ `false` is a keyword, not a macro, so `#ifndef false` is **always true**
and every translation unit including that header received `false` as *int* `0`.
Under `-std=c++23`, libstdc++ 13 writes constraints like `requires … || false`
in `<bits/iterator_concepts.h>`, which then fails with
`error: constraint '0' has type 'int', not 'bool'` — hundreds of times, in any TU
that includes `<string>/<vector>/<algorithm>/<map>` *after* that header.
`game/src/stdafx.h` includes libthecore's stdafx at line 9 and the STL headers at
15-27, so this would have broken essentially all of `game` and `db`. Now guarded
with `#if !(defined(__linux__) && defined(__cplusplus))`; `TRUE`/`FALSE` still
behave.

## libthecore

Changes: a Linux branch in `signal.c` (otherwise the whole file compiles to
nothing and `signal_setup()`/`signal_timer_*()` are undefined at link, and the
SIGCHLD `reap()` handler lives there); `srandomdev()` → `srandom()` + a
`getrandom(2)` reseed in `main.c`; the `false` macro guard above; and a
`uname -s` Makefile with `-fno-strict-aliasing`, because `tea.c`/`des.c`/`gost.c`/
`buffer.c` type-pun through `char*`/`DWORD*` casts that GCC 13 exploits at `-O2`.

The epoll backend already carried both fixes the sister port had learned the hard
way — the one-shot disarm is atomic inside `fdwatch()`, and the timeout converts
`tv_usec/1000` honestly rather than reproducing the FreeBSD branch's
`tv_usec`→`tv_nsec` bug (which waits 1000× less than asked). It had never been
run, so it was tested:

- **Functional: 42 passed, 0 failed.** Timeout honoured (308 ms for a 300 ms
  request), read+write on one fd yielding two separate events as kqueue would,
  one-shot fires exactly once, re-arm after an unconsumed one-shot does not
  stall, EOF, delete-stops-delivery.
- **Soak: 250 clients × 200 × 1400 B — 70,000,000 / 70,000,000 bytes echoed**,
  0 spurious `default:` events (the arm that tears a connection down), 0 premature
  EOF, 0 `fd_rw`/`fd_mask` drift.
- **Measured idle CPU: 0.1 %** (0.001 s over 2.01 s wall, 0 events delivered
  while idle). The sister port's broken first version measured 96.5 %.

## FreeBSD build proven untouched

Not asserted — demonstrated three ways:

1. `unifdef -U__linux__` on every modified file, comments stripped and whitespace
   normalised, diffed against the same treatment of the pristine reference:
   `signal.h`, `fdwatch.h`, `fdwatch.c`, `main.c` are **sha256-identical**.
2. The two files that differ do so in exactly one directive line each, which
   `unifdef` cannot fold. A `cpp` truth table over every `(__FreeBSD__,
   __linux__)` combination a FreeBSD compiler can see shows both old and new
   directives evaluate identically in all cases.
3. Every Makefile variable evaluated with `UNAME_S=FreeBSD` against the pristine
   Makefile: `CC`/`CXX`, `CFLAGS`, `IFLAGS`, `OBJFILES`, `BIN` all identical for
   all five libraries. FreeBSD still gets `clang++-devel`, `-I/usr/local/include`,
   `ar cru`.

## Support libraries — zero source changes

Only Makefiles needed converting. `libpoly` builds only a subset of its sources
(its `main.cc` is a `<windows.h>` test driver, excluded upstream too). `liblua`
is Lua 5.0.3 compiled as **C**, so `register` is a legal storage class and never
became an issue. `libserverkey`'s `::SHA1()` compiles and links against OpenSSL 3.
`libsql` needed nothing: `my_bool` is present in the shipped MariaDB Connector/C
headers, `MYSQL_OPT_RECONNECT` still exists, and **nothing in the whole tree reads
`mysql->reconnect` directly** (0 hits).

`libsql`'s Makefile gained one variable: `DEPFILE`, selected by platform. The
checked-in `Depend` names `/usr/local/include/mysql/*.h` by absolute path and
makes gmake abort with "No rule to make target", so the Linux branch uses
`Depend.linux` instead and leaves the FreeBSD `Depend` untouched. `Depend.linux`
itself is generated by `make dep` and is **not** in the patch — the patch
contains no build output at all, which is what lets a tree that has been
compiled in still produce exactly these bytes.

### libsql proven against a live database

Not just compiled — 29 of 29 checks against MariaDB 10.11.14 using the exact call
sequence `db/src/DBManager.cpp` uses: `Setup`/`Connect` with charset honoured
through `mysql_options`, `DirectQuery` CREATE/INSERT/SELECT with correct
affected-rows and insert-id, `EscapeString` round-tripped byte for byte,
`CLIENT_MULTI_STATEMENTS` walked with `SQLMsg::Next()`, and the **full async
path** — worker thread, `CSemaphore` handshake, `AsyncQuery`/`ReturnQuery`/
`PopResult` with user data intact, clean `Quit()` join.

A whole-set link smoke test pulled one symbol out of every project archive plus
all third-party archives using game's exact flags: one C++ ABI, one word size, no
missing or duplicate symbols.

## Link lines

The dependency tree's location is a Makefile variable, not a hardcoded path:
both ported Makefiles read `M2_EXTERN_LINUX ?= /opt/m2port/extern/Linux40250`,
so one variable repoints both modules. `build-deps-40250.sh` defaults to that
same path; the Docker builder overrides it with
`M2_EXTERN_LINUX=/opt/m2extern EXTERN_DIR=/opt/m2extern` on every `make` line.
`EXTERN` below is shorthand for whatever that resolves to.

The original Makefiles' `-L../../../extern/lib` is left in place and points at
**FreeBSD** objects, which is why the Linux lines put `$(EXTERN)` archives on by
absolute path rather than relying on `-L` search order.

**game:**
```
-L../../libthecore/lib -L../../libpoly -L../../libsql -L../../libgame/lib \
-L../../liblua/lib -L../../libserverkey -L$(EXTERN)/lib \
-lthecore -lpoly -llua -llualib -lsql -lgame -lserverkey \
$(EXTERN)/lib/libcryptopp.a $(EXTERN)/lib/libIL.a \
$(EXTERN)/lib/libmysqlclient.a $(EXTERN)/lib/libssl.a $(EXTERN)/lib/libcrypto.a \
$(EXTERN)/lib/libz.a -lmd -pthread -lm -ldl
```
includes: `-I$(EXTERN)/include -I../../liblua/include -I../../libserverkey`

**db:**
```
-L../../libthecore/lib -L../../libsql -L../../libpoly -L../../libgame/lib -L$(EXTERN)/lib \
-lthecore -lsql -lpoly -lgame \
$(EXTERN)/lib/libmysqlclient.a $(EXTERN)/lib/libssl.a $(EXTERN)/lib/libcrypto.a \
$(EXTERN)/lib/libz.a -pthread -lm -ldl
```
includes: `-I$(EXTERN)/include`

`-ldl` and `-pthread` are mandatory on glibc; FreeBSD did not need `-ldl`.
`/usr/local/lib/mysql/libmysqlclient.a` and `/usr/lib/lib{ssl,crypto,z}.a` are
hardcoded in both Makefiles and do not exist here.

## Standing rule: never define `_TIME_BITS=64`

`sizeof(time_t)` must stay 4 under `-m32`, matching FreeBSD/i386. Seven packed
structs are simultaneously wire format **and** database layout:

| Struct | File | Line |
|---|---|---|
| `TPlayerSkill` (inside the main character row) | `common/tables.h` | 413 |
| `TPacketGiveGuildPriv` | `common/tables.h` | 1092 |
| `TPacketGiveEmpirePriv` | `common/tables.h` | 1099 |
| `TPacketDGChangeGuildPriv` | `common/tables.h` | 1135 |
| `TPacketDGChangeEmpirePriv` | `common/tables.h` | 1144 |
| marriage struct (`tMarryTime`) | `common/tables.h` | 1272 |
| `TPacketGCTime` | `game/src/packet.h` | 1941 |

Measured: with `_TIME_BITS=64` each grows by 4 bytes — `TPlayerSkill` 6 → 10,
`TPacketGCTime` 5 → 9 — which would corrupt the client protocol and the database
with no compiler error. `-D_FILE_OFFSET_BITS=64` alone is safe; it does not
widen `time_t`.

So the port makes it a compiler error. `game/src/packet.h` gained
`static_assert`s on the sizes of the affected structs — the file has no
`#include`s of its own and is pulled into every game translation unit, so the
build stops at the first one rather than shipping a silently different wire
format. `build-deps-40250.sh` aborts if `_TIME_BITS=64` reaches it through the
environment, and the Docker builder stage asserts the same thing on the finished
binaries.
